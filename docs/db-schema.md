# Модель данных бэкенда (Этап 1 — Проектирование)

Описание схемы БД для виджета поиска и объединения дублей amoCRM/Kommo. DDL —
[`backend/db/schema.sql`](../backend/db/schema.sql). СУБД — PostgreSQL (Selectel managed PG,
защищённый сегмент «Облако ФЗ-152»).

## Обзор и связи

```
accounts (1) ─┬─ (1) oauth_tokens
              ├─ (N) entities ──── (N) entity_keys        # индекс поиска дублей
              ├─ (N) rules                                # правила AND/OR на сущность
              ├─ (N) merge_journal ── (N) snapshots       # история объединений + откат
              ├─ (N) scan_jobs                            # фоновое массовое сканирование
              ├─ (N) webhook_events                       # идемпотентность вебхуков
              └─ (N) audit_log                            # аудит (§8)
```

`account_id` — сквозной ключ изоляции данных по аккаунтам (152-ФЗ, §8 ТЗ). Все прикладные
запросы фильтруются по `account_id`.

## Таблицы

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| **accounts** | Подключённые аккаунты (биллинг за аккаунт) | `account_id` PK, `subdomain`, `status`, `plan`, `settings` |
| **oauth_tokens** | Зашифрованная пара токенов OAuth (§7.3/§8) | `access_token_enc`, `refresh_token_enc`, `nonce`, `kms_key_ref`, `*_expires_at`, `rotated_at` |
| **entities** | Реплика ключевых полей сущностей | `entity_type`, `amo_id`, `key_fields`; UNIQUE(`account_id`,`entity_type`,`amo_id`) |
| **entity_keys** | Нормализованные ключи поиска дублей | `key_type`, `key_hash`, `key_norm`; индекс(`account_id`,`entity_type`,`key_type`,`key_hash`) |
| **rules** | Правила поиска (поля + AND/OR) | `entity_type`, `fields`, `operator`, `auto_merge`, `enabled` |
| **merge_journal** | Журнал объединений | `master_amo_id`, `duplicate_amo_id`, `mode`, `author_user_id`, `transferred`, `rolled_back_at` |
| **snapshots** | Снимки дублей для отката (30 дней) | `merge_id`, `amo_id`, `payload`, `expires_at` |
| **scan_jobs** | Фоновые задачи массового сканирования | `status`, `progress`, `total`, `cursor`, `params` |
| **webhook_events** | Идемпотентность приёма вебхуков | PK(`account_id`,`event_id`), `type`, `processed_at` |
| **audit_log** | Аудит операций | `actor`, `action`, `meta` |

## Логика обнаружения дублей

1. Сущность приходит вебхуком/синхронизацией → ключевые поля **нормализуются** (см. ниже).
2. Для каждого ключа считается `key_hash = SHA-256(key_type || ':' || normalized)` и пишется в
   `entity_keys`.
3. Поиск дубля = выборка по индексу `(account_id, entity_type, key_type, key_hash)` — другие
   сущности с тем же хэшем. Правила (`rules`) комбинируют ключи через AND/OR; между правилами — OR.
4. Прямого перебора API amoCRM на каждый запрос нет — работает индекс на стороне бэкенда (§6.2).

## Нормализация значений (§6.1)

| Тип (`key_type`) | Нормализация | Ключ для сравнения |
|---|---|---|
| `phone` | только цифры → E.164 по стране аккаунта | последние 10 цифр (РФ, учёт 7/8) |
| `email` | `trim` + нижний регистр (опц. игнор `+alias` и точек в gmail) | нормализованный email |
| `inn` | только цифры + валидация контрольной суммы (10/12 знаков) | ИНН |
| `name` | `trim` + нижний регистр; для компаний — убрать ОПФ (ООО/АО/ПАО/ИП…), кавычки, лишние пробелы | нормализованное имя |
| `custom` | по типу пользовательского поля | значение |

Нечёткое сравнение (Левенштейн/триграммы) — **2-я итерация** (решение по открытому вопросу №2):
в схеме заложен опциональный GIN/`pg_trgm`-индекс по `key_norm` (закомментирован в `schema.sql`).

## Безопасность (§8)
- Токены — только в зашифрованном виде (AES-GCM, ключ в KMS); открытых значений в БД нет.
- Изоляция по `account_id` во всех прикладных таблицах; токены не переиспользуются между аккаунтами.
- Снимки для отката (`snapshots`) живут по умолчанию 30 дней (`expires_at`), затем удаляются.
- `webhook_events` обеспечивает идемпотентность (повторный вебхук не обрабатывается дважды).
